### Firebase project
`attendance-roaster-7ce62` (client config in `src/firebase.js` — used ONLY for `getAuth()`).
Backend uses a service-account certificate (`Backend/firebasecreds.json` via `FIREBASE_CREDENTIALS_FILE`).

### Firestore collections (defined in `app/core/firebase.py`)

| Collection | Contents / key scheme |
|---|---|
| `admin_list` | CR email documents (doc id = normalized email, set by `/admin/cr`) |
| `admins` | Admin email documents (seeded manually via Firebase Console; checked with `where("email","==",…)` → docs must carry an `email` field) |
| `users` | One doc per Firebase UID. Profile (`uid,name,email,role`) merged on every authorize; plus `student_name`, `enrollment_no`, `enrollment_verified` once a student is confirmed |
| `sessions` | Doc id `SESSION-<12 hex chars>`. Fields: `session_id, session_name, cr_uid, latitude, longitude, radius_meters, status(active/ended), qr_lifetime_seconds, sheet_title, started_at, ended_at, started_by`, and after first QR: `current_qr_hash`, `current_qr_expires_at` |
| `session_state` | Single doc `current` = pointer `{active_session_id, updated_at}` — source of truth for "the one active session" |
| `qr_tokens` | Doc id = **SHA-256 hex of the raw token**. Fields: `session_id, token_hash, token (RAW, stored in plaintext), created_at, expires_at, active, first_scanned_at, window_expires_at` |
| `attendance` | Doc id = `{session_id}__{NORMALIZED-UPPER enrollment}` — one record per student per session: `status PRESENT, marked_at, distance_meters, student_latitude/longitude, client_ip, user_agent, device_hash, name, enrollment_no, session_name` |

### Google Sheets structure (single spreadsheet, `GOOGLE_SHEET_ID`)
- **`Sheet1`** (`GOOGLE_STUDENTS_SHEET_NAME`): master roster `Enrollment No | Name`. Read-only from code; never modified.
- **`Attendance`** (`GOOGLE_SHEET_NAME`): append-only log `Timestamp | Enrollment No | Student Name | Status | Session-ID`.
- **Per-session tabs** `ATT_<last6-of-id>_<cleaned session name>` (max 100 chars): `Enrollment ID | Student Name | Status`, seeded all-`ABSENT`, column A forced to TEXT format, bold header, conditional formats (ABSENT → red bold, PRESENT → green bold). Created on session start, flipped per student on submit.

### Authentication mechanism (IMPORTANT — currently hybrid cookie + header)
1. Client signs in with Google through Firebase Auth `signInWithRedirect`.
2. `AuthContext` bootstrap sends the **Firebase ID token** as `Authorization: Bearer <firebasetoken>` to `POST /authorize-user` (the ONLY endpoint that consumes a Firebase ID token — `routers/auth.py::_bearer_token`).
3. Backend verifies it (`firebase_auth.verify_id_token`), decides the role server-side, upserts `users/{uid}`, mints a **HS256 application JWT** (`sub=uid, role, email, iat, exp`, `exp = now + JWT_EXPIRE_MINUTES` = **3 minutes** by default).
4. The JWT is delivered **twice**: as `HttpOnly` cookie `attendance_jwt` (`Secure; SameSite=None` in production, `Lax` in dev — `core/security.py::apply_auth_cookie`) **and** in the JSON body as `application_token`.
5. The frontend keeps `application_token` **in memory only** (`services/api.js` module variable) and sends it as `Authorization: Bearer <appJWT>` on **every protected request**. Reason: frontend and backend are different sites in production, and browsers drop the third-party cookie; the header is the reliable transport.
6. `get_current_user` (`middleware/auth.py::_application_token`) reads the cookie first, falls back to the Bearer header. Role gates: `require_cr`, `require_student`, `require_admin` (403 with codes `CR_ONLY`/`STUDENT_ONLY`/`ADMIN_ONLY`).
7. 401 handling in `api.js::request`: any 401 (except from `/authorize-user`) triggers `recoverAuth()` → re-runs `getFirebaseIdToken(true)` + `/authorize-user` (refreshes both cookie and in-memory JWT) → retries the original call once → if that fails, `onAuthPermanent()` sets `requiresReauth` and clears the profile.

### Storage usage (verified)
- **Cookie**: `attendance_jwt` — HttpOnly app JWT (mostly discarded cross-site by browsers; kept as same-site/dev fallback).
- **localStorage**: exactly one key — `pending_attendance_return` = JSON `{url, at}`, parked by `startGoogleSignIn()` only when the current path is `/attendance` with a query; consumed once by `takeAttendanceReturnUrl()` with a **10-minute TTL** (`services/auth.js`). Firebase Auth itself also persists the Google session (IndexedDB/localStorage internally).
- **sessionStorage**: not used by app code.
- **In-memory**: the application JWT (`api.js`), the Firebase user object (`AuthContext`).

### QR implementation
The QR is rendered client-side with `QRCodeCanvas` from `session.qr.qr_url`. The URL is
`{PUBLIC_APP_URL}/attendance?token=<raw_token>` (`qr_service.build_qr_url`). The raw token is
`secrets.token_urlsafe(24)` — random, short-lived, **not** a credential; its SHA-256 hash is the
Firestore doc id, but the raw token is ALSO stored in plaintext in the doc (needed later to serve the same QR to all CRs and to validate scans).

## SECTION 3 — CR "START SESSION" FLOW (exact trace)

**Frontend**
1. CR opens `/cr` → `CRRoute` waits for auth → `CRDashboard` mounts.
2. Mount effect calls `api.getActiveSession()` (`GET /active-session`). If a session exists → jumps straight to `active` stage (rejoin, starts clocks). If not → `idle` stage shows `renderStartForm`.
3. CR types a **Session Name** (required client-side) and submits the form → `handleStart()`:
   - `busyRef` guard (first click wins), stage `starting`, fake progress bar (250 ms ticks to 92 %).
   - `await getCurrentLocation()` — **fresh high-accuracy reading**; a denial aborts Start (error shown, back to `idle`).
   - `api.startAttendance(lat, lng, name)` → `POST /start-attendance` body `{latitude, longitude, session_name}`.
4. On response: stores `{session_id, session_name, radius_meters, is_new, qr}`, sets `qrLifetime` from `qr.expires_in_seconds`, starts **two timers**: the QR countdown clock (`startClock`) and the **5 s stats poll** (`startStatsPolling`); clears `seenRef`; stage `active`.

**Backend — `POST /start-attendance`**
1. Dependency `require_cr` → `get_current_user` decodes the app JWT (cookie or Bearer) and checks `role=="cr"` — CR status ultimately comes from the `admin_list` Firestore collection decided at `/authorize-user`.
2. `session_service.create_or_get_session(cr.uid, lat, lng, session_name)` runs a **Firestore transaction** on `session_state/current`:
   - If `active_session_id` points to a doc with `status=="active"` → **join** it (returns `created=False`) — two CRs can never create two sessions.
   - Otherwise: new id `SESSION-<12 HEX>`; transaction writes `sessions/{new_id}` (`status:"active"`, `qr_lifetime_seconds` = server default 10, `sheet_title:None`, `started_at` ISO-UTC, coordinates, radius 30 m) and updates the `current` pointer. All reads precede writes (transaction rule).
3. If newly created (outside the transaction): **best-effort** `sheets_service.create_session_sheet(session_id, session_name)` → adds/reuses tab `ATT_<id6>_<name>`, copies the whole Sheet1 roster with `ABSENT`, applies TEXT format + conditional red/green; the returned title is written to `sessions/{id}.sheet_title`. Wrapped in try/except — the session survives Sheets failures; **Firestore is the source of truth**.
4. `qr_service.get_current_qr(session_id)` (transaction on the session doc) mints the **first QR token** (see Section 4) and returns `{session_id, qr_token, qr_url, expires_in_seconds, countdown_seconds}`.
5. Response → `StartAttendanceResponse{success, session_id, session_name, radius_meters, is_new, qr}`.

```
CR clicks Start
↓ CRDashboard.handleStart()
↓ getCurrentLocation() (browser prompt)
↓ POST /start-attendance {latitude, longitude, session_name}
↓ FastAPI: start_attendance()  [Depends: require_cr]
↓ session_service.create_or_get_session()  [Firestore txn on session_state/current]
↓ sheets_service.create_session_sheet()    [Sheets tab, best-effort, only when created]
↓ qr_service.get_current_qr()              [Firestore txn, first token]
↓ StartAttendanceResponse(+qr) → startClock() + startStatsPolling()
```

## SECTION 4 — QR GENERATION, ROTATION AND LIFETIME (exact trace)

* **Where generated:** only in `qr_service.get_current_qr(session_id)`, called by `/start-attendance`, `/qr/refresh`, and `/active-session`. A Firestore **transaction on the session document** serializes concurrent rotations.
* **What the QR contains:** a URL, `{PUBLIC_APP_URL}/attendance?token=<raw_token>`. The raw token is `secrets.token_urlsafe(24)`. It contains **no session id, no JWT, no personal data** — the session is resolved server-side from the token document.
* **Where stored:** `qr_tokens/{SHA-256(raw)}` with `session_id`, the **raw token in plaintext**, `created_at`, `expires_at`, `active`, `first_scanned_at`, `window_expires_at`; and the session doc keeps pointers `current_qr_hash`, `current_qr_expires_at`. (Hashed *doc id*, but not hashed-for-validation — the raw value must be served back to all CRs.)
* **Reuse vs rotation:** if the current token is unexpired, `active`, and its doc exists → the SAME token is returned to every CR (this is why all CRs show one QR). Rotation happens lazily: on the **first call after expiry**, a new token is created, the old doc is set `active:false`, pointers updated.
* **Token lifetime:** the session's `qr_lifetime_seconds` (default `QR_TOKEN_LIFETIME_SECONDS=10` s). The CR can change it via `POST /qr/lifetime` → `set_qr_lifetime` validates against the **backend allow-list (5,10,15,20,30,60)**; the new value applies **from the next rotation** — the current token keeps its own expiry.
* **Who decides expiration:** **backend only**, via stored server timestamps. The frontend receives two numbers: `expires_in_seconds` (configured lifetime) and `countdown_seconds` (actual remaining at issue time). The browser countdown is display + trigger only: when it hits 0 the dashboard calls `/qr/refresh`, which rotates server-side if needed and resyncs the clock. If no CR polls after expiry, the QR on screen is stale-but-displayed until the next refresh call.
* **What happens when the QR expires (student side):** a scan of an expired, never-scanned token is rejected `QR_EXPIRED` in `scan_token`; an expired *current* check without prior scan is rejected in `validate_token_for_check` (grace = token's own `expires_at` + 1 minute, and only if still `active`).

### ⚠️ Two distinct timers — they are NOT the same mechanism
| | QR TOKEN LIFETIME | STUDENT COMPLETION WINDOW |
|---|---|---|
| Purpose | how long the printed QR stays scannable | how long a student has to finish after scanning |
| Value | per-session, CR-adjustable 5–60 s (default 10 s) | fixed `STUDENT_SESSION_MINUTES=1` → **60 s** |
| Start | token creation (`expires_at`) | **first successful `/attendance/verify-token`** (`first_scanned_at`, `window_expires_at`) |
| Stop | next rotation via `get_current_qr` (or session end / `/end-attendance` invalidation) | enforced at `/attendance/check` (`ATTENDANCE_WINDOW_EXPIRED`); frontend also runs a display countdown |
| Decided by | `qr_service` + session doc | `qr_service.scan_token` + response `window_seconds=60` |
| Frontend role | countdown → calls `/qr/refresh` | countdown → disables buttons; backend re-checks authoritatively |

Note: once a student's `verify-token` succeeded, **rotating the QR does not cancel the student** — the window lives on the token record they already used, and `/attendance/check` validates that same token string (still in their URL) against `window_expires_at`, not against `current_qr_hash`.

## SECTION 5 — STUDENT QR SCAN FLOW (most important — exact trace)

### 5.1 Scan / open link
Student's camera app resolves the URL to `https://<hosting>/?/attendance?token=…`; Firebase Hosting SPA-rewrites to `index.html`; React Router renders `/attendance` → `StudentAttendance`. `token = searchParams.get("token")`; stage = `found` (or `invalid` when the param is missing). **No request is made to the backend at this point** — nothing is validated yet.

### 5.2 Auth background check (parallel, on app boot)
`AuthProvider` mounts: consumes any pending `getRedirectResult`, `onAuthStateChanged` sets `firebaseUser`. A fresh page load briefly has `firebaseUser === undefined` → the Continue button renders disabled as **"Checking sign-in…"** (prevents the historical login loop).

### 5.3 Tapping **Continue** — before reaching the attendance form (`handleContinue`)
1. If `firebaseUser === undefined` → abort (wait; no sign-in fired).
2. If `firebaseUser === null` → **this is where Firebase Google authentication happens**: `login()` → `startGoogleSignIn()` parks the full `/attendance?token=…` URL in localStorage (only that route, 10-min TTL) → `signInWithRedirect` → Google account chooser → **returns to app ROOT `/`** → `getRedirectResult` → `onAuthStateChanged` fires → `POST /authorize-user` sets cookie + returns `application_token` → when `role` is set, the parked-URL effect does `window.location.assign(returnUrl)` back onto `/attendance?token=…`. Student taps Continue again — now signed in.
3. `ensureSession()` — re-runs `getFirebaseIdToken(true)` + `/authorize-user` so the app JWT (cookie AND in-memory Bearer) is guaranteed committed **before** any protected call (this was the fix for the third-party-cookie 401).
4. `getCurrentLocation()` is requested here (best-effort: failure only sets a visible `locationWarning`).
5. `api.verifyToken(token)` → **`POST /attendance/verify-token`** (requires `get_current_user` only — students *and* CRs pass). Backend `qr_service.scan_token`:
   - SHA-256 the raw token → load `qr_tokens/{hash}` → unknown = **400 QR_INVALID**;
   - load its `sessions/{session_id}` → `status != "active"` → **400 SESSION_NOT_ACTIVE**;
   - first-ever scan: token must be `active` AND `now ≤ expires_at` else **400 QR_EXPIRED**; then stamp `first_scanned_at=now`, `window_expires_at=now+60s` on the token doc — **this is the exact moment the student timer starts**;
   - repeat scans (retry flows) skip the stamp and just return the record.
   - Response: `{session_id, window_seconds: 60}` → frontend sets `windowSeconds`/`timeLeft` and starts the display countdown.
6. `api.getStudentMe()` → **`GET /student/me`** (`require_student`) → reads `users/{uid}`; returns `verified` + name + `********001` mask only when `enrollment_no` + `enrollment_verified` exist.
7. Stage routing: returning student → **`welcome`** (skips digit entry entirely); new student → **`last3`** form (3-digit numeric input, buttons auto-disable when the display countdown hits 0).

So before reaching any form, the student traversed: boot auth check → (possibly a full Google redirect round-trip) → explicit re-authorization → geolocation prompt → QR token validation (starting the real 60-s window) → identity lookup in Firestore.

### 5.4 New student only — last-3 lookup
`POST /student/lookup {last3}` (`require_student`). `student_service.resolve_last3`: validates exactly 3 digits → matches against the roster fetched from **Sheet1** (60-second in-process cache; first lookup of a wave pays a Sheets read) → 0 matches = `STUDENT_NOT_FOUND`, >1 = `MULTIPLE_STUDENTS_MATCH`, exactly 1 = returns **name + masked enrollment only** (the full roster never reaches the browser). Stage → `confirm` ("Student Found"). "Not you?" returns to `last3`.

### 5.5 Confirm & submit
`handleSubmit` (from `welcome`/`confirm`/`retry`):
1. `POST /student/confirm {last3}` (`require_student`; idempotent) → backend re-resolves Sheet1, writes `users/{uid}: {student_name, enrollment_no, enrollment_verified:true}` (refuses a *different* saved enrollment: `ENROLLMENT_ALREADY_SET`).
2. **Fresh `getCurrentLocation()`** (strict — a failure here aborts and shows retry).
3. `POST /attendance/check {session_token, latitude, longitude}` (`require_student`). **The body carries no identity** — it comes from `users/{uid}`.

`attendance_service.mark_attendance` checks, in order (all server-side):
1. JWT (dependency) → 2. verified enrollment exists (`ENROLLMENT_NOT_VERIFIED`) → 3–5. `qr_service.validate_token_for_check`: token record exists (`QR_INVALID`) → session active (`SESSION_NOT_ACTIVE`/`SESSION_NOT_FOUND`) → window: if scanned, `now ≤ window_expires_at` else `ATTENDANCE_WINDOW_EXPIRED`; if never scanned, only a still-`active` token within `expires_at + 60 s` grace is redeemable (`QR_EXPIRED`) → 6. enrollment still exists in the Sheet1 roster (`STUDENT_NOT_FOUND`) → 7. **Haversine distance** ≤ session `radius_meters` (30 m default) (`OUTSIDE_LOCATION`) → 8. duplicate check: doc `attendance/{session_id}__{ENROLLMENT}` exists **or** any record with same `student_uid` in this session (`ALREADY_MARKED`, 409).

Writes:
- `attendance/{…}.set` with `status PRESENT`, `marked_at` UTC ISO, `distance_meters`, student coordinates, and **server-observed audit fields** — `client_ip` (first `X-Forwarded-For` entry), `user_agent`, `device_hash = sha256(ip|ua)[:16]` (never sent by the browser).
- `sheets_service.append_attendance_row` → log row in `Attendance` (dd/mm/yyyy HH:MM:SS UTC). **If this fails the Firestore doc is deleted (rollback) and the request errors**, so the student can retry cleanly.
- `sheets_service.mark_student_present(sheet_title, enrollment)` → formula `MATCH` lookup, update `C<row>` = `PRESENT` (conditional format turns it green). Best-effort — never rejects the request.

Response `{status:"PRESENT", marked_at}` → stage `success`. Recoverable failures → `retry` stage with "Try Again" (allowed until the 60-s server window ends); fatal codes (`QR_INVALID/QR_EXPIRED/SESSION_NOT_ACTIVE/SESSION_NOT_FOUND`) → `failed` stage with no actionable button.

### 5.6 When each thing happens (summary table)

| Event | Exact trigger in code |
|---|---|
| Google auth | First Continue tap with `firebaseUser===null` (or Login button) — `login()`/`startGoogleSignIn`; NOT on page load |

| Student data fetched | `GET /student/me` right after verify; `POST /student/lookup` for new students |

## SECTION 6 — AFTER ATTENDANCE IS MARKED / LIVE STATS / DISPLAY / LATENCY

### 6.1 How CR live statistics are retrieved
`startStatsPolling`: every **5 000 ms** `GET /sessions/{session_id}/stats` (`require_cr`). Backend `get_session_stats`:
1. `sessions/{id}.get()` → `session_name`, `status`;
2. `roster_size()` → Sheet1 count (cached 60 s);
3. `attendance.where("session_id","==",id).stream()` — deliberate **single equality query, no orderBy**, then in-memory sort by `marked_at` desc (avoids any composite-index requirement);
4. builds `{total_students, present_count, percentage, recent:[last 10 {name, marked_at}], warnings}`; `warnings` from `_proxy_warnings`: groups by `device_hash` and `client_ip`, emits non-blocking "⚠ Multiple students…" strings (raw values never leave the backend).

The same payload arrives via `GET /active-session` (rejoin) and `GET /sessions/{id}/summary` (end state).

### 6.2 How the CR UI shows newly marked students
- **Popups:** each poll compares `stats.recent` keys `name|marked_at` against the `seenRef` Set; new keys push a `.present-popup` ("Rahul Sharma ✓") into a full-viewport `pointer-events:none` `.popup-layer`; CSS animates them rising from the **bottom** toward the **top-right**, staggered by `index*0.18 s` delay, removed after `POPUP_LIFETIME_MS=4200` ms.
- **Water fill:** fixed `.water-bg` whose inner `.water` height = `stats.percentage` % — the whole screen "fills" as attendance arrives.
- **Session end sync:** any CR's `/end-attendance` sets `status:"ended"`; every other CR's next poll (≤5 s, and ≤ the QR countdown tick hitting `/qr/refresh`, which then errors `SESSION_NOT_ACTIVE`) triggers `showFinalSummary` → final `GET /sessions/{id}/summary` → absentee table (already sorted **ascending by enrollment** server-side) + client-generated CSV (BOM + RFC-4180 quoting + CRLF) + clipboard copy.

### 6.3 Where latency is currently introduced (traceable in code)
1. **Render cold starts** — idle free-tier instance sleep delays the first API call (the `/health` ping pattern exists but nothing in the frontend warms the backend). Affects Continue/verify and QR refresh most.
2. **Synchronous Google Sheets calls inside request handlers:**
   - `/start-attendance` blocks on `create_session_sheet` (add tab + batch update with the whole roster + format calls = multiple Sheets round trips; worst case seconds; caught, but the CR waits).
   - `/attendance/check` blocks on `append_attendance_row` (append; failure triggers delete-rollback + student retry) and on `mark_student_present` (**2 extra Sheets round trips per student: a formula `MATCH` then an update**). Each concurrent submission pays these network latencies serially.
   - First roster use (`lookup`/`confirm`/`stats` after cache expiry) blocks on a full `get_values()` of Sheet1 (60 s cache softens bursts).
3. **gspread client is process-global & non-pooled**; Sheets API calls are not parallelized; many sequential Firestore get/set round trips per check (verify enrollment, token doc, session doc, roster match scan, attendance doc existence, `student_uid` stream scan, set, delete-on-failure).
4. **5 s stats poll granularity** — a mark appears on the CR screen up to 5 s after submission (by design, "no hammering").
5. **QR staleness window** — rotation is lazy (on next `get_current_qr` call). The displayed QR can remain visibly "current" for up to ~1 s past expiry (frontend tick) plus whatever Render latency hits that refresh call; a student scanning in that gap gets `QR_EXPIRED`.
6. **Geolocation up to 15 s** (`timeout:15000`, `maximumAge:0`) on the final submit path — cold GPS fixes dominate perceived time-to-success on phones.
7. **Redirect sign-in cost** — `signInWithRedirect` involves full page loads: to Google, back to `/` (boot + `getRedirectResult` + `/authorize-user`), then `window.location.assign` **another full reload** onto `/attendance`. On slow mobile networks this is multiple seconds.
8. **`ensureSession()` before every Continue** — always forces `getIdToken(true)` (network re-fetch of the Firebase token) + a second `/authorize-user` (2 Firestore membership queries + upsert txn) even when the boot-time authorize just completed. Cheap but redundant; note `_email_in_collection` falls back to **streaming the whole `admin_list`/`admins` collection** whenever the equality query misses.
9. **Pydantic v2 + sync `def` endpoints** run in FastAPI's threadpool — fine at class sizes, but every handler is blocking I/O; concurrent scans serialize behind each other's Sheets/Firestore round trips (per worker).
10. **Single active session pointer** — by design every CR polls/rotates through one Firestore doc transaction; heavy CR-polling contention adds Firestore latency under many open dashboards.
